# CM100 V2

## Purpose

`cm100_v2` is the production gateway implementation for the **Philips Efficia CM100** patient monitor.
It follows the exact same architecture as [`gateway/mp5sc_v2`](</C:/laragon/www/smartward4/gateway/mp5sc_v2>) and [`gateway/vs4_v2`](</C:/laragon/www/smartward4/gateway/vs4_v2>) — store-and-forward SQLite outbox, classified retries, dead-letter, heartbeat telemetry, server-assigned identity — so all gateway types are operated, deployed, and monitored the same way.

The test-flow tool in [`gateway/cm100`](</C:/laragon/www/smartward4/gateway/cm100>) (which wrote `raw/` + `interpreted/` files and sent nothing) stays untouched; its field-proven interpretation rules are ported into v2.

## Where the CM100 sits between the other two machine types

| | MP5SC v2 | VS4 v2 | CM100 v2 |
|---|---|---|---|
| Protocol | Philips proprietary / **UDP** | HL7 ORU^R01 / **MLLP TCP** | HL7 ORU^R01 / **MLLP TCP** |
| Direction | Gateway polls | Monitor pushes | Monitor pushes |
| Style | Continuous | **Spot-check** (1 msg = 1 record) | **Continuous stream** (1 msg ≠ 1 record) |
| Record trigger | BP capture event | Each ORU message | **Profile close** (gap / new BP / max window) |
| Default port | n/a | 4000 | **2575** |

The MLLP transport, outbox, sender, heartbeat, API endpoints and deploy scripts are shared with `vs4_v2`; the CM100-specific part is [`cm100_profile.py`](</C:/laragon/www/smartward4/gateway/cm100_v2/listener/src/cm100_profile.py>).

## Profile grouping (ported from the interpreter)

The CM100 streams ORU^R01 every few seconds (SpO2/Pulse each cycle; NBP/Temp/RR when measured), so single messages are folded into **profiles** per patient (MRN):

- continuous SpO2/Pulse are kept as **min/max ranges** plus the latest point value;
- the latest BP / Temp / RR are carried;
- a profile **closes** — becoming one queued vital-sign record — when:
  - `PROFILE_GAP_SECONDS` (default 120) pass with no readings (monitoring stopped), or
  - a **different blood pressure** is measured (the old BP's context ends), or
  - `PROFILE_MAX_SECONDS` (default 300) elapse, so a stable long-monitored patient still charts a record at a bounded cadence (v2 addition — the old in-place-rewrite behaviour cannot work against a POST-only API).

On shutdown, open profiles are flushed to the queue so buffered readings survive a service restart.

## CM100 quirks handled (learned from real traffic)

- OBX-3 carries the label in **component 2** (`NBPs`, `NBPd`, `NBPm`, `Pulse`, `SpO2`, `Temp`, `RR`, `Perf`); matching is label-based.
- An **empty OBX-5** means "no reading this cycle" (result status X) — skipped, not zero.
- The **device clock is unreliable** (ships as 2013-01-01): `measured_at` is the gateway wall-clock of the last reading, never MSH-7.
- `NBPm` (mean) and `Perf` are ignored (no API field).
- Readings without an MRN are **never guessed onto a patient**: counted in the heartbeat (`skipped_no_patient`) with a rate-limited warning (the stream would otherwise spam the log every few seconds).

## Queue, retries, duplicate protection, heartbeat

Identical to `vs4_v2` / `mp5sc_v2`:

- outbox lifecycle `pending → sent/retry/dead`, WAL + `synchronous=FULL`, FIFO retention, hard size caps;
- failure classes `transient` / `soft` (404) / `hard` (400/422) / `auth` (401/403) with the same caps;
- `gateway_event_id` (SHA-1 of gateway + MRN + profile window + values) sent as `X-Idempotency-Key`;
- heartbeat every 30 s with the same payload shape (`monitor`, `queue`, `power`, `service`, `netwatch`, extended `stats`), so the existing dashboard renders CM100 gateways unchanged; `monitor.listener` adds `open_profiles`.

## Communication with the server

Same endpoints and auth as the other v2 gateways: `POST /api/v1/vital-signs` (idempotent), `POST /gateway/register`, `POST /gateway/heartbeat`, `GET /wards`, `POST /device/login`, optional `GET /monitor-devices` + status push (`USE_API_DEVICES=true`). Credentials are attached only at send time — the queue on disk never contains passwords.

## Local test

```powershell
cd gateway\cm100_v2
copy listener\.env.example listener\.env    # edit as needed
python listener\main.py                     # terminal 1
python test_sender.py 127.0.0.1 2575        # terminal 2
```

The test sender simulates a real stream: SpO2/Pulse cycles fold into one profile, the first NBP joins it, an empty cycle is skipped, a **different** NBP closes profile 1 (queued) and starts profile 2, and a no-MRN cycle is counted but never queued. Stopping the gateway flushes profile 2 to the queue.

## Deployment

- **Raspberry Pi (production):** `deploy_pi/setup.sh` — the same guided 14-step installer (server-assigned name, static monitor-LAN IP with `never-default`, systemd + netwatch, offline-capable, listen-port verification). See [`deploy_pi/README.md`](</C:/laragon/www/smartward4/gateway/cm100_v2/deploy_pi/README.md>).
- **Docker:** `Dockerfile` (expose `LISTEN_PORT` 2575/tcp).

On the CM100, configure the HL7/network export destination to the gateway's **static LAN IP**, port `2575`. A CM100 gateway and a VS4 gateway can share one Pi: they use different ports (2575 / 4000), service names (`cm100` / `vs4`), and data dirs.

## Rollout

1. Deploy on one test Pi; point one CM100 at it.
2. Verify profiles close at the expected cadence and appear in SmartWard.
3. Simulate: network drop, API timeout, Pi reboot, service restart mid-stream — verify queued profiles replay and the shutdown flush works.
4. Only then promote to production use.
